## 0. 이미 확정된 규칙 (재확인)

- **DB 스키마는 절대 수정하지 않는다.** `shopdb2`의 테이블/컬럼/제약조건은 그대로 두고, 필요한 권한/스코프 로직은 전부 애플리케이션(백엔드) 레이어에서 구현한다.
- **문서 파일명 규칙**: `번호_문서명_버전_YYMMDD_HH.MM.md` (버전이 바뀌면 기존 파일을 덮어쓰지 않고 새 파일로 추가, 이전 버전은 보존).
- **기술스택**: 백엔드 FastAPI(Python, `uv`) / DB MySQL / 프론트 React(Node.js).
- **어드민 백엔드 폴더 구조·파일명·도메인 분류(7개)**: [shopdb2_백엔드_파일명_고정규칙_v0.1](../shopdb2_백엔드_파일명_고정규칙_v0.1_2026.09.14.md)에서 확정 — 자세한 내용은 §2 참고.
- **DB 접근 방식**: ORM 사용 확정 (`models/*.py`가 ORM Model을 정의하는 구조로 명시됨). §1의 "ORM vs raw SQL" 항목은 해소됨.

## 2. 파일명 고정 규칙 (어드민 백엔드) — 요약

전체 내용은 원본 문서 [shopdb2_백엔드_파일명_고정규칙_v0.1](../shopdb2_백엔드_파일명_고정규칙_v0.1_2026.09.14.md) 참고. 핵심만 요약합니다.

### 2.1 가장 중요한 원칙
> 같은 기능 = 같은 파일명. **AI가 파일명을 정하지 않는다 — 팀이 먼저 정한 파일명에 AI가 맞춘다.** DB 구조를 AI 편의에 맞춰 바꾸지 않는다.

### 2.2 도메인별 고정 파일 (어드민, 총 29개 기능)

| 도메인 | Router / Schema / Service | Model | 기능 수 |
|---|---|---|---:|
| A. 사용자/조직 | `admin_users.py` | `users.py` | 7 |
| B. 상품/카테고리/재고 | `admin_products.py` | `products.py` | 8 |
| C. 주문/결제 | `admin_orders.py` | `orders.py` | 3 |
| D. 환불 | `admin_refunds.py` | `refunds.py` | 2 |
| E. 파일/미디어 | `admin_files.py` | `files.py` | 3 |
| F. 고객문의/정책 | `admin_support.py` | `support.py` | 2 |
| G. AI/RAG (방향 A 채택 시) | `admin_ai.py` | `ai.py` | 4 |

각 도메인은 `routers/`, `schemas/`, `services/`에 동일한 파일명(`admin_{도메인}.py`)을 사용하고, `models/`만 별도 이름(`{도메인}.py`, admin 접두사 없음)을 씁니다.

### 2.3 오픈 아이템 — 대고객(고객용) 파일명 규칙 (신규)

파일명 고정 규칙 문서는 **어드민 전용**입니다. 대고객 측 API(회원가입/로그인, 상품 조회, 주문/결제, 문의 작성 등, [03_기능정의서](./03_기능정의서_0.1v_260914_11.42.md) 참고)는 아직 파일명 규칙이 없습니다.

- [ ] 대고객 라우터를 어드민과 같은 `app/routers/` 아래 `customer_*.py`(또는 `buyer_*.py`) 접두사로 분리할지, 별도 하위 폴더(`routers/admin/`, `routers/customer/`)로 나눌지 결정
- [ ] `models/*.py`는 어드민/대고객이 같은 테이블을 공유하므로 그대로 재사용(중복 모델 파일 금지)하고, `schemas/`·`services/`만 대고객용을 별도로 둘지 결정
- [ ] 셀러(SELLER) 콘솔을 이번 범위에 포함한다면 동일한 방식으로 `seller_*.py` 네이밍 확정 필요 (문서 02 §4 참고, 아직 범위 미확정)

## 3. P1 — 코드보다 먼저 API 계약 확정

(0.1v와 동일하되, ORM 확정에 따른 항목 하나를 추가했습니다.)

- [ ] **화면별 필요한 API 목록 작성** — [03_기능정의서](./03_기능정의서_0.1v_260914_11.42.md) 기준, 어드민은 §2.2의 29개 기능·7개 도메인 파일에 매핑
- [ ] **Method 확정** — GET/POST/PATCH/DELETE, DELETE가 물리 삭제인지 `active_yn` 비활성화인지 테이블별 구분
- [ ] **Endpoint 이름 확정** — `/api/v1/{리소스명(복수형)}`, 하위 리소스는 경로 중첩, 어드민 prefix(`/api/v1/admin/...`) 여부
- [ ] **Request 구조 확정** — `schemas/*.py`의 Pydantic 스키마로 정의
- [ ] **Response 구조 확정** — envelope 여부, **ORM 모델 → Pydantic 변환 방식 통일** (예: `model_config = {"from_attributes": True}`로 `models/*.py` 인스턴스를 그대로 직렬화할지, 또는 서비스 레이어에서 dict 변환 후 매핑할지 — ORM 확정에 따라 새로 추가된 결정 항목)
- [ ] **Error 구조 확정** — 공통 예외 핸들러 포맷 통일
- [ ] **Pagination 구조 확정** — `page`+`size` vs `offset`+`limit`, `total` 포함 여부
- [ ] **검색/filter parameter 명명법 확정**
- [ ] **ID 이름 통일** — DB 컬럼명 그대로 사용 (`user_id`, `product_id`, `order_id` 등)
- [ ] **날짜 형식 통일** — Asia/Seoul 기준 ISO 8601 여부
- [ ] **상태값 통일** — DB enum 값 그대로 사용 ([01_테이블정의서](./01_테이블정의서_0.1v_260914_11.42.md) 참고)
- [ ] **null 허용 여부 합의** — DB NOT NULL 제약을 Pydantic `Optional` 여부에 그대로 반영
- [ ] **프론트-백엔드 타입 일치 확인** — snake_case 유지 vs camelCase 변환, OpenAPI 스펙을 계약 원본으로 사용할지

## 6. AI 바이브코딩 공통 지시사항 (신규)

[파일명 고정규칙 문서](../shopdb2_백엔드_파일명_고정규칙_v0.1_2026.09.14.md) §5의 지시사항을 프로젝트 전체(어드민+대고객)로 확장한 버전입니다. **3인 모두 각자의 AI 세션 시작 시 아래 내용을 그대로 전달**하는 것을 제안합니다.

```text
이 프로젝트는 3명이 병렬로 개발하고 있으므로 파일명과 폴더 구조를 임의로 변경하면 안 됩니다.

1. '05_백엔드착수전공통합의사항'과 'shopdb2_백엔드_파일명_고정규칙'을 먼저 읽습니다.
2. 해당 기능은 문서에 지정된 Python 파일에서만 구현합니다.
3. 비슷한 이름의 새 파일을 임의로 만들지 않습니다.
   예: admin_user.py, users_admin.py, user_router.py 등 별도 파일 생성 금지
4. DB 테이블명과 컬럼명을 임의로 변경하지 않습니다. (shopdb2 스키마 고정)
5. 기존 코드가 있으면 새로 만들기 전에 반드시 기존 코드를 먼저 확인합니다.
6. 담당 도메인 외 파일은 임의로 수정하지 않습니다.
7. main.py, core/database.py, core/security.py, dependencies/auth.py 등
   공통 파일 수정이 필요하면 바로 수정하지 말고 필요한 변경사항을 먼저 설명합니다.
8. API 계약(엔드포인트, request/response 구조, 에러 포맷, 상태값, 날짜 형식)은
   '05_백엔드착수전공통합의사항' §3에 정의된 규칙을 따릅니다.
9. 구현 완료 후 반드시 아래 내용을 보고합니다.
   - 수정한 파일
   - 추가한 API
   - 주요 변경사항
   - 테스트 방법
   - 다른 담당자에게 영향을 주는 변경사항
```
