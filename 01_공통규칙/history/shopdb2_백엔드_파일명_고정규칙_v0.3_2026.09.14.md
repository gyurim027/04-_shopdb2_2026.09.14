## 5. 3인 작업 분담 및 충돌 방지

### 5.1 어드민 도메인 배분 — 확정

**원칙**: 개수는 10/10/9로 맞추되, **도메인의 router→schema→service→model을 한 사람이 끝까지 통째로 담당**한다. 하나의 `admin_*.py` 파일을 여러 명이 나눠 개발하지 않는다.

| 담당자 | 담당 도메인 | 기능 수 | 고정 파일 (router/schema/service) | Model |
|---|---|---:|---|---|
| **A** | 사용자/조직(7) + 주문/결제(3) | **10** | `admin_users.py`, `admin_orders.py` | `users.py`, `orders.py` |
| **B** | 상품/카테고리/재고(8) + 환불(2) | **10** | `admin_products.py`, `admin_refunds.py` | `products.py`, `refunds.py` |
| **C** | 파일/미디어(3) + 고객문의/정책(2) + AI/RAG(4) | **9** | `admin_files.py`, `admin_support.py`, `admin_ai.py` | `files.py`, `support.py`, `ai.py` |

**1차 개발 순서(C 한정)**: AI/RAG(4개)는 난이도가 높으므로, C는 파일/미디어·고객문의/정책(5개)을 먼저 완료하고, AI/RAG는 A·B가 기본 기능을 끝낸 뒤 3인이 함께 리뷰하며 진행한다.

- [ ] 대고객 측 개발도 같은 3인이 겸할지, 별도 순서로 진행할지 결정 (§2.2와 연결)

### 5.2 공통 파일 소유/수정 규칙

- [ ] `main.py`, `core/database.py`, `core/security.py`, `dependencies/auth.py`는 수정 전 반드시 팀에 먼저 공유
- [ ] PR 리뷰 규칙: 최소 1인 이상 리뷰 후 병합, API 계약(§3) 변경 포함 PR은 3인 모두 확인 후 병합

## 6. AI 바이브코딩 공통 지시사항

각 담당자별 구체 버전은 [작업자별_착수프롬프트](./작업자별_착수프롬프트_0.1v_260914_15.09.md) 참고.

```text
이 프로젝트는 3명이 병렬로 개발하고 있으므로 파일명과 폴더 구조를 임의로 변경하면 안 됩니다.

1. 이 문서('shopdb2_백엔드_파일명_고정규칙')를 먼저 읽습니다.
2. 해당 기능은 문서에 지정된 Python 파일에서만 구현합니다.
3. 비슷한 이름의 새 파일을 임의로 만들지 않습니다.
4. DB 테이블명과 컬럼명을 임의로 변경하지 않습니다. (shopdb2 스키마 고정)
5. 기존 코드가 있으면 새로 만들기 전에 반드시 기존 코드를 먼저 확인합니다.
6. 담당 도메인 외 파일은 임의로 수정하지 않습니다.
7. main.py, core/database.py, core/security.py, dependencies/auth.py 등
   공통 파일 수정이 필요하면 바로 수정하지 말고 필요한 변경사항을 먼저 설명합니다.
8. API 계약(엔드포인트, request/response 구조, 에러 포맷, 상태값, 날짜 형식)은
   이 문서 §3에 정의된 규칙을 따릅니다.
9. 자기 담당 브랜치(§9)에서만 작업하고, main 브랜치에 직접 push하지 않습니다.
10. 구현 완료 후 반드시 아래 내용을 보고합니다.
    - 수정한 파일 / 추가한 API / 주요 변경사항 / 테스트 방법 / 다른 담당자에게 영향을 주는 변경사항
```

## 9. GitHub 브랜치 전략

- 저장소: `https://github.com/gyurim027/04-_shopdb2_2026.09.14-`
- **`main`**: 공통 문서(`01_공통규칙/`)와 DB 백업(`backup/`) 등 3인이 공유하는 내용만 관리. 코드가 준비되면 여기에 실제 배포 가능한 상태만 병합.
- **작업자 브랜치**: `main`에서 분기, 각자 담당 도메인만 작업
  - `dev/A` — 사용자/조직 + 주문/결제
  - `dev/B` — 상품/카테고리/재고 + 환불
  - `dev/C` — 파일/미디어 + 고객문의/정책 + AI/RAG
- **규칙**:
  - `main`에 직접 커밋/푸시하지 않는다. 항상 PR을 통해 병합한다.
  - `main`이 갱신되면(예: 공통 규칙 문서 변경) 각자 `dev/{A,B,C}`로 최신 내용을 받아온다 (`git pull origin main` 또는 rebase).
  - 공통 파일(`core/database.py` 등) 변경이 필요하면 별도 브랜치(`dev/common`)를 만들어 3인이 함께 리뷰 후 병합하는 것을 권장한다.
