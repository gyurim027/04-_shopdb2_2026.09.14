# 사용자 구조 및 서비스 기획 방향성

- 버전: 0.1v (초안)
- 작성일시: 2026-09-14 11:42
- 전제: 현재 DB 구조(`shopdb2`)는 변경하지 않는다. 아래 사용자 구조와 방향성은 모두 기존 스키마만으로 구현 가능한 범위에서 정의한다.
- 참고 문서: [01_테이블정의서](./01_테이블정의서_0.1v_260914_11.42.md)

이 문서의 목적은 하나의 서비스 방향을 확정하는 것이 아니라, 현재 DB가 지원하는 **모든 사용자 구조**와 그로부터 파생 가능한 **서비스 방향성 후보**를 폭넓게 나열하는 것입니다. 이후 어떤 기능을 우선 구축할지는 이 문서를 검토한 뒤 별도로 결정합니다.

---

## 1. 전체 사용자 구조 맵

DB상 사용자 구분은 `roles`(BUYER/SELLER/ADMIN) + `users.org_id`(조직 소속) 두 축의 조합으로 결정됩니다. 하나의 `user_id`가 `user_roles`를 통해 여러 role을 동시에 가질 수도 있습니다(예: SELLER이면서 동시에 다른 조직에서는 다른 역할).

### 1.1 구매자 (BUYER)
- **근거 데이터**: `users` + `user_roles(role=BUYER)`, `user_addresses`, `orders.buyer_user_id`, `refund_requests.buyer_user_id`, `buyer_inquiries.user_id`, `rag_query_logs.user_id`
- **핵심 니즈**: 상품 탐색/구매, 주문·배송 조회, 환불/문의, (선택) AI 상담을 통한 빠른 답변
- **서비스 축**: 대고객(Customer-facing)

### 1.2 판매자 (SELLER)
- **근거 데이터**: `users` + `user_roles(role=SELLER)`, `seller_profiles`(정산 정보), `products.seller_user_id`
- **핵심 니즈**: 본인 상품 등록/관리, 본인 상품 주문 현황 확인, 정산 정보 관리
- **서비스 축**: 대고객과 어드민의 중간 성격 — "셀러 콘솔"이라는 제3의 화면 축으로 별도 취급 가능 (이번 범위에서는 구조만 정의, 화면 구축 여부는 추후 결정)
- **비고**: 현재 `seller_profiles`에는 조직(org_id) 연결이 없고 `user_id`에만 연결됨 — 판매자는 조직 계층과 무관하게 개인/업체 단위로 존재하는 구조

### 1.3 관리자 (ADMIN) — org_id 기반 스코프 구분
`roles`에는 ADMIN 하나만 존재하지만, `users.org_id`가 가리키는 조직의 `org_type`에 따라 실질적인 권한 등급이 갈립니다 (`org_units`: HEADQUARTER → BRANCH → STORE/WAREHOUSE 계층).

| 등급(개념) | 판단 기준 | 접근 범위 |
|---|---|---|
| 최고관리자 | `org_id`가 `org_type='HEADQUARTER'`인 조직 | 전체 조직·전체 테이블 데이터 |
| 지점장 | `org_id`가 `org_type='BRANCH'`인 조직 | 해당 지사 + 그 하위(`parent_org_id`로 연결된 STORE/WAREHOUSE) 데이터 |
| (확장 여지) 매장/창고 담당자 | `org_id`가 `org_type='STORE'` 또는 `'WAREHOUSE'` | 해당 매장/창고 단위 데이터만 (현재 시드 데이터에는 없으나 구조상 가능) |

- **근거 데이터**: `users` + `user_roles(role=ADMIN)`, `org_units`(계층/유형), 그리고 org_id로 스코프가 걸리는 모든 테이블(`orders`, `inventories`, `buyer_inquiries`, `company_policies`, `refund_policies`, `file_assets`, `rag_documents` 등)
- **핵심 니즈**: 자기 권한 범위 내 전체 도메인(상품/주문/재고/문의/정책) 관리, 최고관리자는 조직/정책/AI 설정까지 포함한 전사 관리
- **서비스 축**: 어드민(Admin-facing)

## 2. 어드민 서비스 방향성 후보

org_units 계층 구조가 이미 갖춰져 있다는 점이 이 DB의 가장 강한 신호입니다. 이를 근거로 아래 방향성 후보를 제시합니다.

### 방향 A. 지점별 위임 운영형 통합 관리
- **컨셉**: 본사는 전사 정책/카탈로그를 관리하고, 각 지사는 자기 지사 범위의 재고·주문·문의를 독립적으로 운영하는 프랜차이즈형 관리 구조
- **근거**: `org_units` 계층, `inventories.org_id`, `orders.org_id`, `company_policies.org_id`, `refund_policies.org_id`가 모두 조직 단위로 분리되어 있음
- **장점**: 현재 시드 데이터(본사/전주지사/부산지사)와 정확히 일치, 권한 매트릭스 설계가 명확해짐
- **단점**: 지사가 실제로 독립 운영되는 비즈니스가 아니라면 과한 구조일 수 있음

### 방향 B. 단일 관리자 화면 + 조직 필터형
- **컨셉**: 화면/기능은 하나로 통합하고, 로그인한 관리자의 org_id에 따라 데이터만 필터링되는 단순한 구조 (권한 등급 구분을 화면상 최소화)
- **장점**: 구현이 단순하고 빠르게 MVP 가능
- **단점**: "최고관리자 vs 지점장" 같은 세분화된 기능 차등(예: 정책/AI 설정은 최고관리자만)을 별도 로직으로 계속 얹어야 함

> 두 방향 모두 데이터 구조는 동일(org_id 필터링)하며, 차이는 화면/기능 설계의 세분화 정도입니다. 문서 4(권한매트릭스)는 방향 A를 기준으로 상세화하되, 방향 B로 축소해도 매트릭스를 그대로 활용할 수 있습니다.

## 3. 대고객 서비스 방향성 후보

DB에 `ai_providers`, `rag_documents/chunks/embeddings`, `rag_query_logs`, `buyer_inquiries`가 함께 존재한다는 것은 이미 AI 상담 기능을 염두에 두고 설계된 구조라는 뜻입니다.

### 방향 A. AI 상담 결합형 쇼핑 경험
- **컨셉**: 일반 쇼핑몰 기능(탐색/구매/주문조회) 위에 RAG 기반 AI 챗봇을 결합 — 환불정책/상품안내 등을 `rag_documents`에 색인해두고 구매자 질문에 실시간 답변, 답변 불가 시 `buyer_inquiries`로 에스컬레이션
- **근거**: `rag_documents.document_type`이 이미 REFUND_POLICY/PRODUCT_GUIDE로 시드되어 있음, `rag_query_logs`가 질의응답 이력을 기록하도록 설계됨
- **장점**: DB 설계 의도와 가장 부합, 차별화 포인트가 명확
- **단점**: 실제 LLM 연동(임베딩 생성, 벡터 검색) 구현 난이도가 있음 — 단, 이번 문서 범위(기획)에서는 방향성만 정의

### 방향 B. 표준 이커머스 + 수동 CS
- **컨셉**: AI 기능은 이후 확장 과제로 남겨두고, 우선 표준 쇼핑몰 기능(상품/주문/문의)만 대고객 화면으로 구축, `buyer_inquiries`는 관리자가 수동으로 답변
- **장점**: 빠른 MVP, AI 연동 리스크 없음
- **단점**: `ai_providers`/`rag_*` 테이블이 당분간 미사용 상태로 남음

> 두 방향은 상호 배타적이지 않습니다 — 방향 B로 먼저 구축하고, 이후 방향 A(AI 상담)를 얹는 단계적 접근도 가능합니다.

## 4. 판매자(셀러) 콘솔 방향성 (참고)

이번 범위는 구매자 중심이지만, DB가 판매자 구조를 이미 지원하므로 향후 확장 지점으로 기록합니다.

- **컨셉**: 판매자가 본인 상품(`products.seller_user_id`)과 그 상품의 주문(`order_items.product_id` 경유), 정산 정보(`seller_profiles`)를 관리하는 별도 콘솔
- **현재 구조상 제약**: 판매자별 재고(`inventories`)는 org_id 단위로 관리되어, 판매자가 특정 조직에 소속되지 않으면 재고 데이터 접근 경로가 불명확함 — 실제 구축 시 "판매자가 어느 org_id에 귀속되는가"를 애플리케이션 규칙으로 정의할 필요가 있음 (스키마 변경 없이 가능)
